# PolyTable 性能演进与基准

> 本文档基于 PolyTable 在真实生产负载（数万行规模表格、百人并发协作场景）下的长期演进与实测经验整理。

本文记录 PolyTable 表格主链路在"5 万行 × 70 字段"合成压测下的性能演进：基线 → 三个根因 → 修复 → 验收。所有数字都来自真实测量，测量方法与边界见 §1；它们是合成负载下的参考值，不是服务承诺。

## 1. 测量方法与边界

读懂本文数据前必须了解口径：

- **合成数据**：压测表为脚本生成的 50,000 行 × 70 个数值字段 + 2 个相依公式字段（cells_json 共约 61MB），不含真实业务数据分布。
- **headless 无节流**：浏览器端基准用 Playwright/Chrome headless 并显式关闭后台节流；窗口被遮挡时 Chromium 的 1s 级定时器节流会污染一切计时。
- **longtask / LoAF 口径**：前端卡顿只认 `PerformanceObserver` 的 `longtask` 与 `long-animation-frame`（LoAF 提供函数级归属）+ CDP CPU profiler 的 self-time 榜单；`setInterval` 间隔探测的"1s 帧"是节流假象。
- **客户端失真**：服务端 Python 压测客户端在 >64 并发时受 GIL 影响明显，p50 会显著高于服务端真实耗时（服务端日志单请求耗时是权威值）。正式验收建议 k6/JMeter 等多进程压测工具。
- **单次合成运行**：除标注"多次样本取中位数"外，多数结果为单次运行，不构成对长期稳定性的证明。

## 2. 压测环境

- 合成压测表：50,000 行 × 70 数值字段 + 2 个公式字段（`formula_a = [字段1]+[字段2]`，`formula_b = [formula_a]*2`），首行结果 3/6、末行结果 150000/300000 供正确性核对。
- 应用参数：`-Xmx3g`、Hikari 16 连接、Tomcat 80 线程（与 [application.yml](../src/main/resources/application.yml) 默认值一致）。
- 压测客户端：服务端本机多进程脚本 + 浏览器 headless 基准脚本。

## 3. 基线压测与三个根因

### 3.1 基线数据（优化前）

| 场景 | 并发 | 结果 |
|---|---|---|
| records_first（首屏 4000 行 gzip） | 1 | p50 228ms，1.34MB/req |
| 同上 | 8 | p50 756ms |
| 同上 | 16 | p50 2.4s，QPS 反降到 6.3 |
| 同上 | 32 | **p50 3.9s + 33 失败，日志 14 次 Java heap space OOM** |
| meta_poll（metaOnly 5s 轮询） | 32 用户 | p50 987ms |
| 同上 | 64 用户 | p50 1.72s |
| 同上 | 100 用户 | p50 2.76s（延迟随用户数线性膨胀） |
| records_drain（全量 13 页） | 1 | 2.3s/用户 |
| 同上 | 8 | 约 10s/用户 |
| rows_full（JSON 全量 5 万行） | 1 | 1.24s，80MB |

### 3.2 三个根因（按发现顺序）

1. **OOM → 连接池毒化连锁**：32 并发首屏时，每个请求并发构建"4000 行 ×（LinkedHashMap + 稀疏对 + Jackson + gzip）"约 30–50MB 堆，3GB 堆被打爆。更严重的是 OOM 会把池内连接打成半读/流失步状态，Hikari 的 `SELECT 1` 借出测试检测不出，之后哪怕 6 QPS 的轮询也报 `Column not found`（S0022）/ `Not a navigable ResultSet` 等鬼错误——这些异常全是次生噪音。重启即恢复；纯 JDBC 最小复现（32 线程 × 同查询）1600/1600 全过，证明驱动与 MySQL 无辜，问题在应用层内存。
2. **轮询全表扫描**：metaOnly 每次做 `contentSyncToken`（COUNT+SUM(version)+MAX(update_time)）+ `countActive`（又一次 COUNT）两次全表扫描；100 人 5s 轮询 = 每秒约 40 次扫描打满 MySQL CPU。
3. **首屏无编码缓存**：空白表 `/records` 路径没接入编码缓存，32 个并发每个都重做"DB → 行对象 → 稀疏 → gzip"全流程。

## 4. 优化措施与效果

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 1 | 表级水位/计数/字段元数据缓存 | `OpsSheetMetaCacheService` | 水位/计数/字段均 2s TTL；**写路径主动 evict**（行仓库全部 mutator 挂钩）——对齐飞书 Bitable"表级 revision 计数器，读路径 O(1)"的公开行为 |
| 2 | metaOnly 整响应缓存 | 同上 + controller | key 含 tableId+角色，5s TTL + 写 evict；保存后下一次轮询立即可见 |
| 3 | 首屏编码缓存接入 /records | controller + `OpsSheetListRecordsEncodeCache` | key = `sheet\|tableId\|viewId\|syncToken\|limit\|kw\|flags`；90s TTL；缓存块扩展 nextCursor/hasMore |
| 4 | 重载闸门 | `ServerLoadGuard` | 信号量包住大页加载 miss 路径，排队超时返回 429；metaOnly/增量/缓存命中不受限 |
| 5 | 热路径 GET 去 `@Transactional` | controller | 排队等闸门的请求不再占死连接池 |

### 4.1 优化后数据（同矩阵复测）

| 场景 | 并发 | 基线 → 优化后 | 提升 |
|---|---|---|---|
| records_first | 1 | 228ms → **9.4ms**（缓存命中）/ 612ms（冷） | ~24× |
| 同上 | 8 | 756ms → **17.1ms** | ~44× |
| 同上 | 16 | 2.4s → **44.8ms** | ~53×（QPS 6.3→290） |
| 同上 | 32 | 3.9s + OOM + 33 错误 → **89.9ms，0 错误 0 OOM** | 修复 |
| meta_poll | 100 用户 | 2.76s → **0.47s p50**（服务端实测单请求 1.0ms；470ms 为 Python GIL 客户端失真） | ~6× |
| records_drain | 1 | 2.29s → 1.50s | 35% |
| 同上 | 8 | 9.98s → 7.47s | 25% |
| write_cell（真实保存） | 4 | —（基线未测） | **p50 39ms** |

正确性验证：保存后水位 token 立即变化（evict 生效）、乐观锁版本推进正常、公式首行/末行对齐、50,000 行 13 页全量取齐无缺行。

### 4.2 存储层索引（在线 DDL）

EXPLAIN 证实并修复两处存储层问题（在线 DDL，`ALGORITHM=INPLACE, LOCK=NONE`，5 万行 0.35s）：

| 问题 | 修复 | 效果 |
|---|---|---|
| delta 增量（`update_time > X`）扫 22,704 行 + filesort | `idx_sheet_row_tbl_del_updated(table_id, deleted, update_time)` | 7 行 covering index |
| 键集分页 sort_order 并列时 filesort（粘贴批次同行 sort_order） | `idx_sheet_row_sort_tiebreak(table_id, deleted, sort_order, create_time, row_id)` | 深翻页 3 行，写延迟仍约 2ms |

## 5. SSE 变更推送

推送实现与架构决策见 [architecture.md §5](architecture.md#5-协作变更推送sse)。性能实测：

| 指标 | 结果 |
|---|---|
| 100 条 SSE 并发订阅，一次写入 | 100/100 全部收到信号 |
| 写完成 → 客户端收到推送 | **p50 0.1ms / max 0.2ms** |
| 对比纯轮询变更可见延迟（均值） | 约 2.5s → 0.1ms（约 25,000×） |

1 次写 = 100 次 emitter.send（异步单线程），写事务零阻塞。

## 6. 增量编码 stale-while-revalidate（"先旧后新"）

高频编辑会把首屏编码缓存打穿（写一次失效一次，并发打开首屏就反复重编码）。改进：

- 编码缓存 key 去掉 syncToken，块内记录生成时水位；写操作后**旧块继续服务**（客户端靠 SSE 推送 + sinceMs 增量收敛，飞书式"先旧后新"），同时后台单线程串行重编码（key 去重，防内存尖峰）。
- 响应带 `recordsEncodeCacheStale` 标记供观测；重编码走独立闸门，失败放弃本轮（TTL 内旧块兜底）。

数据（写入进行中反复开首屏，8 用户每 2s 保存一次）：

| 指标 | 改进前（写打穿缓存） | 改进后（stale-while-revalidate） |
|---|---|---|
| 首屏 p50 | 24ms | **23ms**（持平） |
| 首屏 p95 | **2.85s** | **571ms**（约 5×） |
| 收敛验证 | — | 写后立即 stale=true，53ms 服务旧块；约 3s 后后台重编码完成 stale=false |

全量回归：drain p50 2.3s → **879ms**；32 并发首屏 96/96 通过 p50 44.7ms；meta_poll 0 错误；0 新增 OOM。

## 7. 100 人混合场景验收

### 7.1 多进程客户端，60s 窗口

负载：100 人 5s 轮询（4 进程 × 25 用户）+ 8 人持续开首屏（96 次）+ 4 人全量 13 页翻页（8 次）+ 6 人并发编辑（18 次保存，期间水位持续变化）。

| 场景 | 请求数 | 错误 | p50 | p95 | 说明 |
|---|---:|---:|---:|---:|---|
| meta_poll ×4 进程 | 1200 | **0** | 0.5s* | 0.77s | *客户端 GIL 失真；服务端单请求 1ms |
| records_first | 96 | **0** | 24ms | 2.85s | p95 = 写入使缓存失效后的重编码（预期行为） |
| records_drain | 8 | **0** | 11.3s | 12.2s | 与 100 轮询+编辑共享 4 vCPU 下的全量拉齐 |
| write_cell | 18 | **0** | 129ms | 267ms | 混合负载下的真实保存 |

全程 0 错误、0 OOM、0 次生错误；服务 active、health UP。

### 7.2 90s 混合窗口复核

负载：100 人轮询（4 进程 × 25 用户 × 90s × 5s 间隔）+ 2 进程 × 8 workers 开首屏（160 次）+ 全量翻页（2 次）+ 编辑保存（12 次）。

| 场景 | 请求数 | 错误 | 延迟解读 |
|---|---:|---:|---|
| meta_poll ×4 进程 | **1800** | **0** | min 0.9–1.9ms（服务端真实速度）；p50 约 500ms 为客户端 100 锁步线程调度失真 |
| records_first ×2 进程 | **160** | **0** | p50 13.5ms；p95 1.7–2.5s = 重启后首个冷编码（之后全缓存命中） |
| records_drain | 2 | **0** | 886ms / 3.99s（并发负载下 13 页全量） |
| write_cell | 12 | **0** | p50 111ms（开表突发并发期） |

**验收结论：100 人同时在线 + 高频请求 + 页面操作 + 编辑的全混合场景，服务端 0 错误、0 OOM。**

## 8. 公式与编码基准（JVM 内存合成负载）

环境：macOS arm64、OpenJDK 17.0.2、Node.js 22、Chrome 156。数据边界：仅使用 JVM 内存中生成的数据，未连接数据库。固定生成 50,000 行 × 70 个基础字段（输入值由行号和字段号确定），每行计算两个公式，结果经 NDJSON 单响应 writer 写入只计字节的输出流。同一测试重复三次取中位数。

| 指标 | 样本 1 | 样本 2 | 样本 3 | 中位数 |
|---|---:|---:|---:|---:|
| 公式求值（50,000 行 × 2 公式） | 413 ms | 207 ms | 253 ms | **253 ms** |
| NDJSON 编码 | 465 ms | 395 ms | 276 ms | **395 ms** |
| writer 首字节 | 237 ms | 241 ms | 161 ms | 237 ms |
| 响应字节数 | 24,349,301 | 24,349,301 | 24,349,301 | 24,349,301 |

- "writer 首字节"含服务端在首帧前扫描全部行以收集统一字段键的耗时。
- Node.js 端以惰性 ReadableStream 消费同一结构：NDJSON 解码约 583ms，只创建一个 body reader，以最多 128 行的回调批次消费，不保留完整行集；页面流式回调复用解码器行数组、只为新批次更新 key 集合（此前每批复制旧行并重建 key 集合会造成 O(n²) 重复遍历）。
- 该基准是公式计算与内存行对象编码的合成测试，**不包含**真实 SQL 查询、字段/公式配置加载、缓存冷热差异、HTTP 容器缓冲、压缩、网络与浏览器解码。

## 10. `/rows` 全量 vs `/records` 分页对比（参考机）

在 8 vCPU / 8GiB 参考机上，对同一张 50,000 行 × 70 数值字段 + 2 公式字段的合成表做了两条路径的对比（单次合成运行，客户端与压测口径见 §1）：

| 路径与负载 | 结果 | 耗时 | 说明 |
|---|---|---|---|
| `/rows` 全量 JSON，外部客户端 1 并发 | 1/1 成功，50,000 行；公式首尾正确 | 26.82s | 响应约 80MB；含客户端到服务器的网络传输 |
| `/rows` 全量 JSON，外部客户端 2 并发 | 2/2 成功，均为 50,000 行 | 50.53–51.58s | 网络传输成为明显耗时因素 |
| `/rows` 全量 JSON，本机客户端 4 并发 | 4/4 成功 | 5.11–5.65s | 每响应约 80MB；应用进程 RSS 约 3.45 GiB |
| `/rows` 全量 JSON，本机客户端 8 并发 | 出现 HTTP 500 | 约 20 秒内触发 | 应用日志记录 2 次 `Java heap space`；之后健康检查超时；重启应用后恢复 |
| `/records` 分页路径，本机客户端 1 并发 | 50,000 行、13 页全部完成 | **3.89s** | 传输合计约 75.6MB（gzip 列式编码） |
| `/records` 分页路径，本机客户端 8 并发 | 8/8 全部完成 50,000 行、13 页 | 每用户 10.82–11.67s | **未见 OOM**，Java RSS 采样峰值约 2.73 GiB |

结论：JSON 全量路径在高并发下堆内存不可控（这也是 `/records` 成为默认路径的原因）；分页稀疏列式路径在同等数据量、更高并发下稳定完成。注意外部客户端 `/rows` 耗时包含网络传输，不能与本机数据直接比较；`/records` 通过不能等同于所有访问路径通过——`/rows` 的高并发堆内存仍是已知待处理限制。

## 11. 剩余已知限制

1. **`/rows` 全量路径高并发堆内存不足**：见 §10，大表请使用默认 `/records` 路径；长期方向是给全量路径加流式/分块输出。
2. **delta 增量路径未缓存**：token 变化后的增量拉取仍按行查（数据量小，影响有限）。
3. **编码缓存被写打穿的残余场景**：stale-while-revalidate 已把 p95 从 2.85s 压到 571ms，但高频编辑下重编码本身仍是单线程串行；可演进到按 dirty 行合并的增量编码。
4. **公式无依赖图增量计算**：每次请求全行重算（有编译缓存与行级物化），依赖图 DAG 方案见 [architecture.md §7](architecture.md#7-字段类型全集规划)。
5. **客户端测量上限**：Python 压测客户端 >64 并发时 GIL 失真明显；正式验收建议 k6/JMeter 多进程压测。
